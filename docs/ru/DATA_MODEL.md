# Модель данных и версии

[English](../DATA_MODEL.md) · [Русский](DATA_MODEL.md) · [Документация](../../README.ru.md#документация)

SQLite хранит актуальные сущности и сохранённые решения, файлы — исходные доказательства и точные версии документов. Их связывают ID и хеши. Изменение текста HTML-отчёта не изменяет базу.

## Файлы пространства

| Путь | Назначение |
| --- | --- |
| `workspace.json` | Версия схемы и признак синтетического пространства |
| `settings.json` | Источники, политика, бюджеты и рендеринг |
| `facts.json` | Текущие факты кандидата и два профиля |
| `journal.sqlite` | JSON-записи, реестр артефактов, метаданные |
| `facts-history/`, `evidence/` | Сохранённые наборы фактов и локальные доказательства |
| `snapshots/` | Оригиналы ответов API и HTML |
| `packages/`, `reviews/` | Версии документов, задания, проверки |
| `activities/`, `activity-artifacts/` | Запросы/результаты навыков и копии входов/выходов с хешами |
| `learning/`, `report/` | Планы и формируемые локальные представления |
| `imports/`, `legacy/` | Оригинал миграции и старые файлы |

## Имена файлов артефактов

Создаваемые файлы называются `<ГГГГ-ММ-ДД>-<контекст>-<префикс sha256><расширение>` внутри своего каталога, например `learning/2026-09-14-product-demo-platform-lead-53275ec9.json`, `reviews/2026-09-14-master-product-v-86bc5079e2f59c79-content-cbfd1f49.json` или `evidence/2026-09-14-verified-distinctions-1bc1969f.md`. Дата — когда материал попал в журнал, контекст — что это (трек и вакансия, пакет/версия/вид ревью, исходное имя файла), восьмисимвольный хеш связывает имя с зарегистрированной контрольной суммой и делает его уникальным. Повторная регистрация того же содержимого в том же каталоге переиспользует файл. Сохранённые имена старых файлов остаются понятными, но сокращаются до 200 байт — меньше лимита 255 байт распространённых файловых систем.

Всё это приватные данные. Внутренние пути артефактов относительны пространству; метаданные activity могут содержать абсолютный путь рабочего оригинала и не предназначены для публикации.

## Таблицы и сущности

`records(kind TEXT, id TEXT, payload TEXT)` имеет составной первичный ключ. `artifacts(path, sha256, bytes)` учитывает неизменяемые байты, `meta(key, value)` — метаданные runtime. Гибкость JSON не означает полную проверку схемы: используйте контракты CLI, проверяйте контролируемые операции Store и сохраняйте события.

| Вид записи | Связи и содержание |
| --- | --- |
| `companies` | ID компании, профиль бизнеса, доказательства размера, ссылки на досье |
| `vacancies` | ID компании/провайдера/объявления, URL, наблюдение, доступность, требования и допуски |
| `observations` | Неизменяемая связь вакансии, источника, снимка и нормализованных данных |
| `current_assessments`, `current_learning` | Указатели актуальной оценки и плана подготовки для вакансии/трека |
| `superseded_records` | Архив прежних результатов (`kind`, `record_id`, `superseded_by`, полный `payload`), убранных из активных видов записей |
| `text_translations` | Русский и английский варианты одного точного текста журнала (ID — хеш текста) и модель переводчика |
| `assessments` | Вакансия + трек + хеш входов; доказательства требований и решение правил |
| `packages` | Мастер/вакансия + трек, текущая версия и история |
| `events` | Операция, ID сущностей, подробности и время |
| `source_health` | Попытка/успех, статус, HTTP, счётчики, сетевой маршрут (`direct`, `proxy`, `proxy_fallback`), следующая попытка |
| `activities`, `activity_events` | Работа hosted-навыка, исполнитель, результат и связи с событиями CLI |
| `company_dossiers`, `text_revisions`, `cover_letters` | Исследования и самостоятельные авторские материалы |
| `interview_plans`, `interview_practices`, `interview_feedback`, `interview_progress` | План → реальная практика → обратная связь → решение о прогрессе |
| `employer_responses` | Полученные ответы с доказательствами и ссылкой на зарегистрированную отправку |
| `submissions` | Подтверждённая пользователем отправка с точной версией |
| `collection_runs` | Один прогон сбора: `new` — ID новых вакансий, `changed` — ID с именами полей, `unchanged` — число без изменений, `possible_duplicates` (автоматически не сливаются), `errors` источников со статусом, HTTP-кодом, причиной и последним успехом, `relevance` — новые вакансии по ступеням и `screened_out` — карточки вне профиля, не добавленные источниками с `skip_off_profile` |
| `relevance_reviews` | Оценки по смыслу от флагманского агента: для каждой вакансии вердикт, балл 0–100 в диапазоне вердикта, трек, сводка, причины fit/gap/risk и id фактов, с хэшами прочитанной вакансии и фактов для устаревания |
| `preparation_overviews` | Общий обзор подготовки по обоим трекам от агента: темы с меткой доказанности, недельный план, банк вопросов, истории и советы по резюме (см. [подготовку](PREPARATION.md#модуль-подготовка-два-входа-и-цикл-практики)) |
| `preparation_briefs`, `track_plans`, `practice_sessions`, `practice_attempts`, `practice_reviews` | Памятки к вакансиям с происхождением; планы по общим пробелам или базовые; вопросы практики (связь с планом через `plan_id`, `plan_kind` и `topic_id`), ответы (артефакты) со ссылками на повтор и уточнение и разборы (см. [подготовку](PREPARATION.md#модуль-подготовка-два-входа-и-цикл-практики)) |
| `cv_edits`, `cv_edit_decisions`, `cv_imports` | Предложенные правки точной версии резюме; неизменяемые решения пользователя с `sequence`; структура импортированного резюме и задача извлечения фактов (см. [CV-профили](CV_PROFILES.md)) |
| `inbox_requests` | Заявка из веб-интерфейса (`type`, `base{kind,id,version}`, `payload`) со статусом `pending`, `applied`, `queued_for_agent`, `conflict`, `failed` или `rejected`, результатом `result` или ошибкой `error` |
| `tasks` | Работа для агентской сессии: `type`, `skill`, статус `queued`, `running`, `blocked`, `failed` или `done`, связанные ID `related`, `request_id`, `activity_id`, `result_refs` |

### Версии записей и заявки

Версия записи — первые 16 шестнадцатеричных символов SHA-256 от канонического JSON (`Store.version`). `Store.patch(kind, id, changes, expected_version, reason)` меняет поля верхнего уровня в одной транзакции `BEGIN IMMEDIATE`: если сохранённая версия отличается от `expected_version`, ничего не записывается (`VersionConflict`); иначе запись обновляется, а событие `record_updated` хранит изменённые поля до и после, обе версии и причину. Поле со значением `null` удаляется; `id` не меняется.

Веб-интерфейс не пишет в журнал. Он сохраняет заявки как `requests/<id>.json` в каталоге состояния. `ajh inbox import` копирует их в `inbox_requests`, а `ajh inbox apply` применяет каждую в отдельной транзакции: заявка, меняющая запись, несёт версию, которую видел пользователь, поэтому запись, изменённая в промежутке, даёт `conflict`, а не потерянное обновление. Детерминированные типы применяются контролируемыми операциями: `vacancy_decision` (личное `interested`/`not_interested` с причиной или `cleared`; доказательства не меняются), `clarification_answer`, `coding_requirement` (`required`/`not_required`/`unknown` с основанием и источником), `evaluate`, `vacancy_add` (ссылка или текст), `cv_edit_decision` (`accept`, `reject` или `edit` с текстом), `cv_import` (вставленный текст резюме и трек), `prep_plan`, `prep_create`, `practice_answer` и `campaign_upsert` (проверка по версии сохранённой кампании; `null` для новой). Заявки, требующие авторской или исследовательской работы, создают `tasks`; агентская сессия берёт задачу через `ajh tasks next`, запускает activity с `related.task_id`, и задача повторяет реальный итог activity (`running` → `done`, `blocked` или `failed`). Задача никогда не становится выполненной без завершённой activity.

## Факты кандидата

Минимальный вымышленный пример:

```json
{
  "schema_version": 1,
  "candidate": {"name": "Алексей Примеров", "contacts": ["alex@example.invalid"]},
  "facts": [{
    "id": "example-platform",
    "text": "Руководил вымышленным платформенным проектом.",
    "section": "experience",
    "verification": "self_reported",
    "claim_type": "historical",
    "sources": ["evidence-note.md"],
    "tracks": ["product", "technical-leadership"],
    "tags": ["platforms"],
    "substantive": true
  }],
  "profiles": {
    "product": {"headline": "Продуктовое руководство", "summary": "Синтетический пример.", "distinction_ids": []},
    "technical-leadership": {"headline": "Техническое руководство", "summary": "Синтетический пример.", "distinction_ids": []}
  }
}
```

До импорта создайте реальный `evidence-note.md` рядом с JSON. Строка, не являющаяся URL, считается путём и копируется в хранилище доказательств. Импорт проверяет уникальность ID, ровно два профиля, наличие источников и классификацию проверки, сохраняет `original_sources` и старый/новый набор фактов.

`verified` — зафиксированная оценка доказательств, а не автоматический эффект импорта. `self_reported` и `conflicting` остаются видимыми. `claim_type: target` не подтверждает достигнутый результат. Сохраняйте контекст работодателя/клиента/партнёра, официальную должность, период и личный вклад.

## Карточки компании и вакансии

Досье поддерживает `about`, `business_areas`, продукты, рынки, сегменты клиентов и сведения о найме со ссылками. Размер описывается через `metric`, `value`, `as_of`, `scope`, `source_url` и confidence/reliability. Отсутствующее число сотрудников нельзя заменить догадкой.

Вакансии нужны `id`, `company_id`, `title`, канонические `urls` и целевой трек/треки. Отдельно храните `role_family`, `role_type`, `level.raw`, `level.source`, `market`, `availability`, `status_checked_on`. Сбор не создаёт надёжной разметки уровня и семейства роли автоматически.

### Условия и даты вакансии

`conditions` (метод `conditions-v1`) хранит то, что указал источник, у каждого значения есть `source`:

| Поле | Содержание |
| --- | --- |
| `salary` | `min`, `max`, `currency`, `period` (`month`, `year`, `hour`, `unknown`), `gross_net` (`gross`, `net`, `unknown`), исходная формулировка `raw` и `source`; `null`, если оплата не указана. Одна сумма появляется только если её дал источник; месячная величина не вычисляется |
| `provider_conversion` | Пересчёт поставщика (например, месячная оценка LinkedIn Salaries в USD) отдельно от вилки работодателя |
| `work_mode`, `employment`, `language` | `{value, source, raw?}`; `value` — `remote`/`hybrid`/`office`, `full_time`/`part_time`/`contract`/`internship`/`temporary`, список кодов языков ISO или `unknown` |
| `posting_language` | Язык сохранённого текста (`ru`, `en`, `unknown`), не требование |
| `allowed_geography` | `status` `listed` (явный список стран), `office_location` или `unknown`, плюс `countries`, `basis` и `source`. Удалённая работа без списка стран остаётся `unknown` |
| `published_on`, `updated_on`, `valid_through` | Даты, опубликованные источником |

Обнаружение (`first_seen`), последнее появление в выдаче (`last_seen`) и проверка (`status_checked_on`, проверки доступности) хранятся отдельно от публикации. При сборе `status_checked_on` ставит только собственная доска работодателя (Greenhouse, Lever, Ashby, HH); карточки агрегатора, корпоративные страницы и replay — нет. Слияние сохраняет известные условия, если новый источник о них молчит, не заменяет более полный текст (`full` > `page_text` > `excerpt` > карточка) и не превращает записанную доступность в `unknown`.

`ajh vacancy add` сохраняет исходный ответ или вставленный текст в `snapshots/intake/` и объединяет его как наблюдение источника `intake`. Компания, не найденная по названию или alias, создаётся с `needs_review: true`.

### Кампании поиска

`settings.json → campaigns[]` описывает, что ищет пользователь: `id`, `name`, `market` (`ru`, `intl`, `any`), `track`, `role_titles`, `levels`, `work_countries`, `work_modes`, `languages`, `employment`, `salary {min, currency, period, gross_net}`, `exclusions`, `source_ids`, `active`. Сравнение вакансии с кампанией даёт по каждому критерию `match`, `mismatch` или `unknown` с основанием и общий итог (любое несоответствие → `mismatch`, любое неизвестное → `unknown`). Зарплата в другой валюте или за другой период — `unknown`: пересчёт не предполагается. Кампании — только предпочтения и не меняют оценку квалификации; вакансия остаётся одной записью, даже если подходит нескольким кампаниям. Некорректный список кампаний игнорируется целиком, и это видно в интерфейсе.

Веб-интерфейс сохраняет эти поля в `payload` записи API. Отдельный `display.location` содержит `raw`, `country`, `city` и `remote` для отображения и фильтров. Используются явные поля страны/города и поддержанные однозначные форматы; неподдержанные места остаются неизвестными. Это не миграция записей и не замена исходной локации. Удалённый формат не означает разрешение работать из любой страны. Контракт API и размещения — в [веб-интерфейсе](DASHBOARD.md).

Требование содержит стабильный `id`, `text`, `source`, `mandatory`, необязательный `tag`, `evidence_fact_ids`, `evidence_reviewed`, `gap_type`. Поля `minimum_years`, `authorization`, `license` обозначают структурный пробел. `language_gate`, `eligibility_gate`, `role_family_gates[TRACK]` фиксируют самостоятельные pass/fail/неизвестно решения.

`record companies PATH` и `record vacancies PATH` **заменяют запись целиком**. Прочитайте текущую карточку и явно объедините изменения в приватном JSON. ID и одно новое поле не являются частичным обновлением и приведут к потере остальных полей.

### Релевантность профилю (вычисляется, не хранится)

Интерфейс добавляет каждой вакансии `display.relevance`: `tier` (`strong`, `possible`, `weak`, `off_profile`), `relevant`, `score` (термометр 0–100), `parts` (`role`, `level`, `domains`, `evidence`), `method` (`rules` или `agent`), `rules` (ступень и балл правил, когда решает оценка агента), `review` (последняя оценка агента с признаком `stale`), `tracks`, `level` (`top`, `lead`, `below`, `company_specific`, `unknown`), `domains[{id, in_title, in_text, facts}]`, `queries[{id, name, query, include, matched, terms}]`, `reasons[{code, terms|tracks|domains|query}]` и `text_checked`. Часть правил пересчитывается при каждой загрузке из названия, сохранённого текста, компании, локации, фактов и `settings.json → relevance` и никогда не записывается в карточку вакансии; оценки агента хранятся в `relevance_reviews`. См. [релевантность профилю](RELEVANCE.md).

## Оценки и документы

### Объяснимое соответствие (`evidence-rules-v2`)

У оценки есть `outcome` — без процента и без вероятности найма:

| Результат | Когда |
| --- | --- |
| `insufficient_data` | Нет размеченных требований или нет подтверждённых фактов по треку |
| `not_fit_mandatory` | Обязательное требование с подтверждённым несоответствием (`confirmed_unmet`, разрешение на работу `no` в `settings.candidate`) или невыполненное обязательное ограничение |
| `has_questions` | Обязательное требование не подтверждено или ограничение неизвестно |
| `fits_verified` | Все обязательные требования подтверждены просмотренными фактами, все ограничения выполнены |

`not_assessed` показывается, если оценки нет. `reason` называет первый блокирующий пункт; `reason_ref` указывает на него (`requirement`, `constraint`, `data`, `all_mandatory`) с `code`. Строка `requirements` содержит `category` (`qualification`, `constraint`), `mandatory`, `evidence` (`fact_id`, `verification`, `source`), `suggested_facts`, `status` (`match`, `gap`, `unknown`), `basis` со стабильным `basis_code` и `action.type`:

| Ситуация | Статус → действие |
| --- | --- |
| Привязаны подтверждённые факты, просмотрены (`evidence_reviewed`) | `match` → `none` |
| Привязаны подтверждённые факты, не просмотрены | `unknown` → `cv_edit` |
| Структурное требование (стаж, разрешение, лицензия) без доказательств | `unknown` → `clarify` |
| Подтверждённые факты с тем же тегом или `experience_framing` | `unknown` → `cv_edit` — отсутствие слова в резюме не означает отсутствие опыта |
| Аннотатор сравнил и доказательств не нашёл (`evidence_checked: true`) | `gap` → `preparation` |
| Ещё не сравнивалось (одного тега недостаточно, чтобы доказать отсутствие) | `unknown` → `clarify` |
| Подтверждённое несоответствие | `gap` → `decision_basis` |

`constraints` содержит `track`, `seniority`, `language`, `eligibility` и, если заданы в `settings.candidate`, `geography` (разрешённые страны против `work_countries`) и `required_languages`; каждое — `pass`, `fail` или `unknown` с основанием. `preferences` — совпадения с кампаниями поиска, они не меняют результат. `completeness` — полнота описания, число требований и подтверждённых фактов по треку. Прежнее поле `decision` сохраняется для старых читателей.

`inputs` хранит дайджесты по частям (`vacancy` без полей доступности, проверок и личного решения, `company`, `facts`, `policy`, `candidate`). Указатель `current_assessments` хранит `checked_inputs` и `checked_at` последнего запуска, даже если неизменный вывод сохранил прежнюю запись; веб-интерфейс сравнивает их с текущим журналом и помечает оценку как требующую обновления с перечнем изменившихся частей. `ajh evaluate --stale` пересчитывает только такие оценки. Требования заменяются через `ajh vacancy requirements ID PATH` с проверкой ID, текста, `mandatory`, `gap_type` (`knowledge`, `practice`, `experience_framing`, `structural`), `category`, ID фактов и флагов. Ответы на уточнения (заявки `clarification_answer`) хранятся в вакансии с ID требования, видны в матрице и делают оценку устаревшей до пересчёта.

Хеш оценки включает вакансию, компанию, факты и политику. Решения правил: `priority`, `needs_clarification`, `not_suitable`, `watch`. Тег лишь предлагает факт; покрытие требует проверенной связи с подтверждённым фактом, который не является целью. Это консервативные правила, а не семантическая модель ранжирования.

Повторный запуск `evaluate` или `learn` для той же вакансии и трека не копит дубли: неизменный вывод сохраняет текущую запись даже при обновлённых входах, а изменившийся становится текущим, прежний переносится в `superseded_records`.

`availability_check` вакансии хранит последнюю автоматическую проверку (`status`, `reason`, `confidence`, `evidence`, `http_status`, `final_url`, `checked_at`, `method`), `availability_history` — последние 20. Определённый результат также выставляет `availability` и `status_checked_on`; правила описаны в [CLI](CLI.md#доступность-переводы-и-обслуживание).

Версия пакета сохраняет исходник, PDF, текст, письмо при наличии, контекст, покрытие, задание, автора, вклад редакторов, число страниц и хеши. Неизменённые входы используют прежнюю версию; новые создают новую. Ревью привязано к полному набору хешей и `version_id`.

Самостоятельное письмо связано с точным CV-пакетом, версией и хешем CV. Оно остаётся черновиком до включения в проверенный пакет. Запись редактирования связывает «до», «после» и пояснения; старый пакет не меняется.

Синтаксис — в [CLI](CLI.md), activity-контракты — в [работе агентов](AGENT_WORKFLOWS.md), проверка и миграция — в [эксплуатации](OPERATIONS.md).
